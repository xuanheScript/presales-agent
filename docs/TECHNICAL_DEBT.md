## P1：Breakdown 有界分批结构化输出

### 背景

当前 CSV 协议的初衷是避免一次生成巨大 JSON 导致上下文或输出尺寸溢出。直接替换为单次大型 `Output.object()` 会重新引入这一问题，因此不采用。

当前仅保留安全修补：模型 `finishReason !== 'stop'` 时拒绝把截断结果作为完整报价继续处理。

### 推荐方案：有界 Map-Reduce

1. **需求切片**：按业务章节和语义边界切分，为每个分片生成应用侧来源 ID。
2. **功能发现**：每个分片通过小型 `Output.array()` 只返回本分片功能候选，并限制输入 token、输出条数和执行时间。
3. **确定性归并**：应用侧规范化、去重，生成稳定的 `FUN-*` ID；模型不反复回显完整需求或完整功能对象。
4. **角色目录**：单独生成有界的 `ROLE-*` 角色集合。
5. **批量工时估算**：按 8–12 个功能一批，仅通过 ID 关联角色和功能。
6. **额外工作识别**：独立的小型结构化调用生成非功能性及项目级工作项。
7. **本地校验**：检查功能覆盖率、ID 引用、角色覆盖、数值范围、重复项和批次完整性。
8. **失败处理**：批次校验失败时有限修复；仍失败则二分批次。CSV 只作为单功能或极小批次的最终降级，不作为主协议。
9. **总预算保护**：超过同步时间或批次数上限时转异步任务或明确失败，不静默截断。

### 迁移顺序

1. 先将“角色工时估算”迁移为小批结构化输出，保持功能发现协议不变。
2. 验证稳定 ID、批次校验和成本结果兼容后，再迁移功能发现。
3. 最后移除主路径 CSV，并保留受控降级和版本标记（建议 `batched_structured_v2`）。

### 验收标准

- 任一模型调用均有明确的输入、输出数组、时间和重试上限。
- 截断或批次缺失不能进入成本计算和持久化。
- 同一输入的 ID、归并和校验结果可重复。
- 大需求不会依赖一个包含全部功能的超大结构化响应。
